结论对假设的逐条判定

原假设：标题摘要采集与书签整理在前，RAG 同步在后。

成立采集 → 归档

归档的 AI 选目录会读 pages 摘要与 class:<id> 标签，采集是它的数据上游； 没有采集结果时归档退化为「标题 + 域名」猜测，置信度掉到 low。

成立采集 → 同步

两者共用 pages 缓存（同一 normUrl 键）。采集先跑且缓存有效时，RAG 的 autoCapture 可复用缓存， 省一次外网抓取；并发时可能重复抓取，动态页面的两次结果也可能不同；不能承诺时序不影响结果。

部分RAG 在最后执行

方向对、机制不同。RAG 由书签事件后 1.5s debounce 触发，往往在采集队列（1.2s 定时器 + 30s alarm + 60s 租约） 和人工确认（可能数小时）之前就完成了首轮入库。

不成立「整理完成后再同步」

归档的 AI 建议必须人工 adopt 才 move。若真等它完成，书签在几天内都进不了云端索引。 代码选择的是乐观同步：先入库、归档后靠 revision++ 补传一版。

不成立三者存在统一编排

没有 orchestrator。三条队列各自用 alarm + 租约抢跑，模块间零调用。 所谓「顺序」只是数据可见性的结果，不是被保证的调度。

修正后的表述：A、B 是 C 的上游数据源；C 以 revision 水位 + 内容指纹自愈追平，而不是等待 A、B 完成。 真正被强制的顺序只有两处：C 内部的 rebuild → reconcile → ingest，以及 bookmarks 事件 → 1.5s debounce → markDirty。

附验证中发现的两个一致性缺口

都能从代码直接定位，建议纳入下一轮修复。

  1. 标签应用不触发同步，后台正常运行时通常等下一轮 reconcile。applyOne 只写 IndexedDB 的 class:<id>， 而 IndexedDB 不产生 storage.onChanged，也不产生书签事件。若这次应用没改标题，RAG 要等到 reconcile（dirty 置位或距上次 ≥1h）才会带上标签补传。修复：applyOne 末尾补一次 SyncEngine.markDirty(false)。
  2. 同一 URL 可能被并发抓两次。BookmarkEnrich.captureOne 与 RAG 的 CaptureAdapters.read 走同一个 PageInfo.getMany，但没有 URL 级 in-flight 锁， 只有 4 路并发上限。新收藏写入的瞬间两条链路同时起跑时，会打两次外网。修复：在 PageInfo 内按 normUrl 和采集上下文做请求去重；force、认证身份、采集方式不同的请求不得错误复用。

实施约束用业务门槛和变更通知保持一致

以下取代旧版“串行等待、移除标签指纹、省近一半上传”等建议，不作未经测量的收益承诺。

  1. 人工信息先形成闭环。复用 QuickTags 的 label、aliases，扩展 note 和编辑时间；覆盖新增、编辑、撤销、导入导出、备份与配置隔离。不能只加输入框却在重载时丢字段。
  2. 变化主动通知，人工确认不阻塞正文。标题和分类标签落盘后标脏；个人称呼变更刷新本地读模型。后台运行、队列和配额会影响实际完成时间，不以“秒级一致”作固定承诺。
  3. 稳定指纹保留真实检索信息。当前目录、分类标签存在于上传文本中，不能只从指纹移除以省请求。同文档短期任务先合并；独立元数据接口须确认后端支持后再设计。
  4. 门禁拒绝不等于自动删除。timeout 先诊断 VPN/本地到首尔及服务上游链路；临时失败保留合格旧版，400/422 或采集器不支持不证明死链；合法短正文不按 200 字符硬排除。首次 404 到期用新请求复核。
  5. 清理与恢复共同验收。删除保存实际云端 ID 和持久化意图；删除成功才标清除。主动恢复巡检、失败重试和版本竞态未验收前，不启用自动失效删除。
