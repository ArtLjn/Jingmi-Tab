## 4. 遗留风险

1. **没有真实模型基线**：所有 AI 断言都跑在替身上，真实首 token 延迟、超时率、token 花费未知；p95 目标暂时无法判定。
2. **覆盖率的真实性依赖真实书签**：`withBody` 只看 `status === 'ok' && text`，没有区分「采到的是导航壳」还是「正文」，动态站点的覆盖率会偏高。
3. **体检误报**：无正文与长期未读会同时命中同一条书签，报告条数偏高；同内容指纹按整页 hash 比对，模板化站点（同一 CMS）容易误判重复。
4. **补全队列与归档队列各自为政**：同一次收藏可能触发两条独立的后台链路，模型调用与采集各算一次预算，成本与耗时会叠加。
5. **未提交改动较多**（23 个文件）：本轮验收针对工作区状态，若后续 rebase 或回滚，需要重新跑一遍 143 项。

## 5. 建议的下一步

1. 补 3 个可验收的小口子：书签空间缺口数、abort 断言、阶段耗时落库（`enrich:metrics` 或 `ai:metrics`），让 v1.15.x 全部可勾。
2. 体检报告加两个动作（补采正文、同网址去重）并复用 `enrich:applied` 的批次撤销，v1.16 的「批量操作可撤销」即可成立。
3. 用真实 Key 跑一轮 100 次计时，按第 2.1 节口径记录冷/热缓存与 RAG 开关，产出第一份 p50/p95 基线，再决定是否开展变更摘要。
