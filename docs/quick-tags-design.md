# 快捷标签（@ Quick Jump）功能设计方案

> 版本 v0.1 · 待评审
> 适用对象：静谧新标签页（Chrome MV3，`manifest.json` v1.9.0）
> 关联已有能力：`/` 本地书签检索、`?` AI 检索

---

## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 用什么触发 | 搜索框**首字符** `@`，与 `/`、`?` 构成三态互斥的前缀指令 |
| 标签从哪来 | **推荐方案 C（混合）**：系统自动生成候选，用户一键确认并命名 |
| 为什么不选纯自动 | 自动学习算得出"高频"，算不出"该被记住"；命名质量直接决定 `@` 是否可用 |
| 为什么不选纯手动 | 冷启动为空，实测多数用户上线后标签数长期为 0 |
| 首发是否要 `history` 权限 | **不要**。书签 + `topSites` 已足够跑通，`history` 作为可选深度模式默认关闭 |
| 关键设计约束 | `@` 是跳转原语而非搜索原语 → **精确率优先于召回率**，宁可少给不可给错 |

## 1. 定位与边界

### 1.1 一句话定位

在搜索框里用 `@` 直接跳到一个"我给它起过名字的地方"，全程不碰鼠标、不做联想猜测。

### 1.2 与现有前缀的关系

现有实现（`js/newtab.js`）用首字符判定模式，`@` 天然可以复用同一套管线：

| 前缀 | 模式 | 语义 | 提交行为 |
| --- | --- | --- | --- |
| 无 | 搜索 | 交给搜索引擎 | 回车搜索网页 |
| `/` | 书签检索 | 在全部书签中**找** | 回车打开高亮项 |
| `?` | AI 检索 | 用自然语言**描述**要找的东西 | 首次回车发起检索 |
| `@` | 快捷标签 | 我已经知道要去哪，**直达** | 回车立即跳转 |

三者的心理模型是递进的：不确定在哪 → `/`；只记得内容 → `?`；非常确定 → `@`。因此 `@` 的交互必须比前两者更快、更"无脑"。

### 1.3 明确不做

- 不做全量 URL 输入解析（那是地址栏的职责）
- 不做标签内的多级路径浏览（只做一层跳转 + 可选路径后缀）
- 不做云同步标签（首发只做本机，导出 JSON 兜底）

## 2. 功能需求

优先级：🔴 P0 首发必须 / 🟡 P1 首发可延 / 🟢 P2 后续

### 2.1 触发与模式

| 编号 | 需求 | 说明 | 优先级 |
| --- | --- | --- | --- |
| FR-01 | 首字符 `@` 进入标签模式 | 仅在 `value[0] === '@'` 时触发。任意位置输入不触发，避免干扰 Gmail / 微博 / Instagram 式的 `@handle` 搜索 | 🔴 |
| FR-02 | 空查询也展开面板 | 只输入 `@` 时立刻列出全部固定标签，降低"想不起来叫什么"的负担 | 🔴 |
| FR-03 | 三态互斥 | `?` > `/` > `@`，由首字符唯一决定，不做组合前缀 | 🔴 |
| FR-04 | 退出即复原 | `Esc` 清空并退出；删光 `@` 后回到普通搜索态 | 🔴 |
| FR-05 | 功能可关闭 | 设置项 `tags.enabled`，关闭后 `@` 按普通字符参与搜索 | 🟡 |

### 2.2 匹配

| 编号 | 需求 | 说明 | 优先级 |
| --- | --- | --- | --- |
| FR-06 | 三级匹配并按序加权 | ① 名称前缀精确 → ② 别名 / 拼音首字母 → ③ 域名或 URL 片段 | 🔴 |
| FR-07 | 大小写不敏感 | `@Git` = `@git` | 🔴 |
| FR-08 | 词首缩写 | `@gh` 命中 GitHub、`@ys` 命中 YS 应收（camelCase 与全大写词组取首字母）。**v1.10 已实现英文部分**；中文拼音首字母需拼音表，留 v1.11 | 🟡 |
| FR-09 | 不做模糊纠错 | 拼错就是没有结果。跳转场景里"猜错"的代价高于"没给" | 🔴 |
| FR-10 | IME 组合期不触发过滤 | 监听 `compositionstart/end`，中文输入法拼写过程中不重新计算，避免候选跳动 | 🔴 |

> FR-10 是现有 `onInput()` 尚未处理的坑：当前 `/` 与 `?` 只匹配 ASCII，问题不明显；`@` 后大概率跟中文，必须补上。

### 2.3 面板与提交

| 编号 | 需求 | 说明 | 优先级 |
| --- | --- | --- | --- |
| FR-11 | 三分区展示 | 固定区（人工确认，顺序可控）/ 常用区（自动候选）/ 新建区（无匹配时出现） | 🔴 |
| FR-12 | 条目信息 | favicon、标签名、域名副标题；固定区显示自定义序号 | 🔴 |
| FR-13 | Enter 当前页跳转 | 直接 `location.href`，替换掉新标签页本身 | 🔴 |
| FR-14 | ⌘/Ctrl+Enter 新标签打开 | 走 `chrome.tabs.create`，保留当前新标签页 | 🟡 |
| FR-15 | Tab 补全为 chip | 补全后进入"标签 + 路径后缀"编辑态，`@gh/pulls` → `https://github.com/pulls` | 🟡 |
| FR-16 | 键盘全可达 | ↑↓ / Ctrl+n,p 选择，Home/End 首尾，符合 listbox ARIA 规范 | 🔴 |

### 2.4 管理

| 编号 | 需求 | 说明 | 优先级 |
| --- | --- | --- | --- |
| FR-19 | 面板内快捷管理 | `Shift+Delete` 删除、`P` 固定、`E` 重命名，不离开输入框 | 🟡 |
| FR-20 | 右键书签 → 设为快捷标签 | 需新增 `contextMenus` 权限，`contexts: ["bookmark"]` | 🟡 |
| FR-21 | 工作台「快捷标签」页 | 列表、拖拽排序、批量删除、JSON 导入导出 | 🟡 |
| FR-22 | 连续删除即拉黑 | 同一候选被删除 3 次 → 写入 `blocked` 永久不再生成 | 🟡 |
| FR-23 | 容量上限与淘汰 | 标签总数 ≤ 500，超出按 `lastUsed` LRU 淘汰自动项（不动手工项） | 🟢 |

### 2.5 非功能

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| NFR-01 | 面板响应 | 100 条标签下过滤耗时 < 30ms；标签常驻内存，不在 keypress 里读 IndexedDB |
| NFR-02 | 首屏不阻塞 | 标签异步加载，未就绪时面板显示"标签加载中…"，与现有 `bmReady` 文案风格一致 |
| NFR-03 | 数据本机 | 不落任何远端；`history` 只在本地聚合，永不上传 |
| NFR-04 | 可清空 | 工作台提供"清空学习数据"，一键删除全部自动候选 |

## 3. 标签来源机制：两种方案

### 3.1 方案 A · 系统自动学习

**信号来源（按权限成本从低到高）**

| 信号 | 权限 | 特点 |
| --- | --- | --- |
| 书签 | `bookmarks`（已授权） | 零成本，标题可用，但只覆盖"主动收藏过的" |
| 常访站点 | `topSites`（安装期权限） | 零弹窗、由 Chrome 本地统计，是 A 方案的主力信号 |
| 浏览历史 | `history`（optional，需用户手势申请） | 覆盖最全，但会弹"读取您的浏览记录"，劝退率高 |
| 本扩展内点击 | 无 | 只覆盖已经被 `@` 或书签空间点过的，属于冷启动之后的补充 |

> `topSites` 拿不到访问次数与时间，只能拿到"访问最多"的排序列表，因此它适合做**候选召回**，不适合单独做**排序依据**。

**打分**

```
frecency(host) = Σ_i exp(-Δdays_i / 14) * w(type_i)
w: 地址栏直接输入 = 3，书签点击 = 2，链接跳转 = 1

score = frecency * (1 + 0.2 * ln(1 + manualHit))
```

**过滤规则（必须做，否则面板会被垃圾填满）**

- 排除搜索引擎域名（bing / google / baidu / 站内搜索页）
- 排除 `chrome://`、`chrome-extension://`、`file://`
- 排除 URL 含 `utm_*`、`redirect`、`login?goto=` 的中转地址
- 同 host 多条路径只取最高分一条；固定标签已占用的 host 不再重复出候选
- 阈值：`score ≥ 3` 且 30 天内访问过，取 Top 12

**无法获取的信号（要如实承认）**

新标签页没有 `tabs` / `webNavigation` 权限，拿不到**停留时长**。因此只能用"同日重复访问次数"与"地址栏直接输入"作为意图代理，这也是 A 方案精度上不去的根因之一。

**优点**：零操作、装完即有、覆盖率随时间增长。
**缺点**：
1. 命名垃圾。自动生成的名称只能取 `document.title` 或域名，实际拿到的是"XX管理系统 - 统一身份认证"这类，用户永远记不住该敲什么。
2. 精度不可控。每天点开 OA 打卡的人，OA 一定排第一；报税季的税务站、招聘季的招聘站会短期冲榜再消失（分数漂移）。
3. 隐私成本。要覆盖"没收藏但常去"的站就必须申请 `history`，而这类提示在扩展商店里是差评高发区。
4. 不可解释。用户会问"凭什么它在第一个"，而答案是一个他无法干预的衰减公式。

### 3.2 方案 B · 用户手动创建

**创建入口**

1. 右键浏览器书签 → "设为快捷标签"（最高效，命中已有心智）
2. `@` 面板底部 → "＋ 新建标签"
3. 输入一个陌生 URL 时 → 提示"是否把它设为快捷标签"
4. 工作台「快捷标签」页 → 表单新建

**数据**：`label`（用户起的名字）、`aliases`（别名与拼音）、`url`、`pin` 顺序。

**优点**：命名质量最高（用户会写"打卡""报销""YS 应收"）、零误报、零额外权限、完全可预期、不会漂移。
**缺点**：
1. **冷启动为空**。功能刚装上是死的，用户的第一印象是"这东西没用"。
2. **持续维护成本**。站点改名、URL 变更、离职换岗，都需要回来改。
3. **用户不勤奋**。这是致命项——纯 B 方案上线三个月后，绝大多数用户标签数仍是个位数甚至 0，功能名存实亡。
4. 发现性差。新建入口再顺，用户也不会为了一个"可能有用"的功能主动配置。

### 3.3 对比

| 维度 | A 自动学习 | B 手动创建 | 说明 |
| --- | --- | --- | --- |
| 冷启动 | 🟢 装完即有候选 | 🔴 空 | 决定性差异 |
| 覆盖率 | 🟢 高 | 🔴 取决于勤奋度 | |
| 命名质量 | 🔴 网页标题 | 🟢 用户语言 | **决定 `@` 能否被记住** |
| 误报率 | 🔴 高（任务性访问、中转页） | 🟢 零 | |
| 维护成本 | 🟡 需定期清理，但用户不知从哪清 | 🟡 需主动建，但有清理边界 | |
| 隐私与权限 | 🔴 深度模式需 `history` | 🟢 零权限 | |
| 可解释性 | 🔴 黑盒排序 | 🟢 完全可预期 | |
| 长期稳定性 | 🔴 随行为漂移 | 🟢 稳定 | |
| 实现复杂度 | 🟡 打分、去噪、去重、衰减任务 | 🟢 CRUD | |
| 失败形态 | 面板塞满垃圾，用户放弃 | 面板空空，用户忘记 | |

**关键判断**

`@` 是**跳转原语**。搜索可以靠召回率兜底（多给几条让用户挑），跳转只能靠精确率——给错一条，用户要清空重来，比没有这个功能更烦。这决定了纯自动方案在这个交互里天然吃亏。

同时 `@` 面板必须是"少而准"的，典型可用规模就是 8–15 个。自动学习产出的是"高频"而不是"该被记住的"：OA、工单、监控面板这类任务性访问频次极高但语义上不该占据快捷位。

反过来，纯 B 的死因是用户不配置。所以既不能全自动，也不能全手动。

## 4. 推荐方案 C · 自动候选 + 人工确认

### 4.1 职责切分

**自动负责"有哪些"，人负责"叫什么、排第几"。**

- 自动层：从书签 + `topSites`（可选 `history`）生成候选，负责召回、打分、去噪、排序
- 人工层：一次点击完成"固定 + 可改名"，之后永久生效，不再被算法改动
- 未确认的候选：留在"常用区"，可随时固定或删除；删除即降权，三次删除永久拉黑

这样既解决冷启动（装完就有 3–8 个候选），又解决命名与精度（进入主展示区必须先过人这一关）。

### 4.2 面板结构

```
@ ─────────────────────────────────────────
固定                                    4
  1  打卡          oa.hongdi.com
  2  YS 应收       yonyou.com
  3  GitHub        github.com
  4  广州仓看板    8.145.50.4:8000
常用 · 系统推荐                          3
  ○  顺丰月结      sf-express.com      [固定]
  ○  Figma         figma.com           [固定]
  ○  税务申报      chinatax.gov.cn     [固定]
─────────────────────────────────────────
↑↓ 选择   Enter 跳转   Tab 补全   ⌫ 删除
```

- 固定区最多 8 个，超出后由用户在面板里置顶替换（不做自动挤占）
- 常用区固定 3 个槽位，避免长尾把面板撑长
- 无匹配时第三区变为"＋ 把「xxx」创建为快捷标签"

实际渲染（替身数据），原图见 `assets/screenshots/`：`quick-tags-panel.jpg`（空查询）、`quick-tags-filter.jpg`（输入 `@gh`）、`tag-manager-collapsed.jpg`（管理页）、`tag-manager-expanded.jpg`（展开 12 条候选）、`tag-manager-narrow.jpg`（900px 单列）。

## 5. 数据结构与存储

### 5.1 标签对象

```js
{
  id: 'tag_1725000000_x7f',
  kind: 'manual' | 'auto',        // manual 一旦固定即转 manual
  label: 'YS 应收',                // 展示名，manual 必填
  aliases: ['应收', 'ysys'],       // 别名 + 拼音首字母
  url: 'https://xxx.yonyoucloud.com/',
  host: 'xxx.yonyoucloud.com',
  pathPrefix: '/',                 // Tab 补全时的挂载点
  pin: 0,                          // 0..n，仅 manual 有效；-1 表示未固定
  hits: 12,
  lastUsed: 1725000000000,
  score: 8.6,                      // auto 专用，每日后台重算
  createdAt, updatedAt,
  blocked: false
}
```

### 5.2 存储分工

v1.10 落地的实际选择（与初版方案的差异见下方说明）：

| 数据 | 位置 | 理由 |
| --- | --- | --- |
| 手动标签 + 候选隐藏次数 + 候选使用次数 | `chrome.storage.local` 的 `newtab.tags.v1`（`js/quick-tags.js`） | 量级 ≤ 200 条（约 60 KB），远低于配额；原子写入、无需 schema 迁移、可直接导出 |
| 自动候选 | **不落库**，每次打开新标签页即时重算 | 信号本来就活；存下来只会随时间腐坏，这正是自动方案"标签自己跑偏"的根因 |
| 开关 | `store.js` DEFAULTS 的 `tags.enabled` | 与现有 settings 同层，随「恢复默认」一起重置 |
| 导入导出 | 单文件 JSON，含 `version` 与 `exportedAt` | v1.11 工作台页面实现 |

> 与初版方案的差异：原计划在 `db.js` 升到 VERSION 4、新增 `tags` store 存全部标签。实现时改为"只持久化人的决定"——手动标签、隐藏次数、使用次数；候选完全由 `bookmarks` + `topSites` 现算。好处是不需要 IDB 迁移、不会出现候选陈旧、也不需要在 `sw.js` 里加每日衰减任务（v1.10 因此没有后台改动）。若后续标签量或查询复杂度上来，再迁入 IndexedDB 只需换 `readStore/writeStore` 两个函数。

**淘汰策略**：`MAX_MANUAL = 200`，超出后拒绝新建并提示先删除；v1.11 工作台再加 LRU。

### 6.1 管理页布局规则（错落卡片）

四张卡如果排成等宽 2×2，会显得呆板，且数据一多就把下方卡片顶出视口。采用「主栏 + 侧栏」双列流：

| 规则 | 实现 | 目的 |
| --- | --- | --- |
| 结构 | `.tag-manager-grid` 两列 grid → `.tag-col.is-side`（固定/已忽略/数据）+ `.tag-col.is-main`（系统推荐） | 一高一矮形成主次，不再四宫格 |
| 高度 | 卡片高度由内容决定；列表折叠 6 行，展开后 `.tag-list.is-scroll` 限高 = 8 行整高（`8 × 46px - 2px`）并内部滚动 | 数据量再大也不会撑高卡片；整行高度避免滚动边界切半行 |
| 间距 | 列间 16px、卡间 16px；侧栏 `justify-content: space-between` 把余量均分到卡间距 | 三张矮卡之间留出呼吸感，节奏拉开 |
| 错位 | 主栏 `padding-top: 14px` | 首卡不与侧栏首卡齐平，形成垂直错落 |
| 齐平 | 两列 `align-items: stretch` + 主栏卡 `flex: 1` | 底边严格对齐，错落但不失衡 |
| 余量 | 主栏 `.tag-more { margin-top: auto }` | 拉伸出的空白落在列表与按钮之间，被「展开其余 N 个」解释掉 |
| 响应式 | ≤980px 合并单列，`display: contents` + `order` 重排为「固定 → 推荐 → 已忽略 → 数据」，偏移归零、限高降到 6 行 | 窄屏不会出现无意义的偏移，推荐也不会被挤到最后 |

**复用点**：`acHits` / `acIndex` / `renderPanel()` / `moveSel()` / `activate()` 这套既有机制原样承接——`@` 模式只是把标签包成 `{ tag, row: { title, url, host } }` 塞进 `acHits`，`activate()` 里加一行回写即可，没有第二套键盘导航实现。

## 7. 权限与隐私

| 权限 | 用途 | 何时申请 | 商店披露 |
| --- | --- | --- | --- |
| `bookmarks` | 已有 | 安装期 | 已在用 |
| `topSites` | 常访站点候选 | 安装期 | 需写明"仅本地统计常用站点，不上传" |
| `history`（可选） | 覆盖未收藏的常访站 | 用户在设置页**点击按钮**后 `chrome.permissions.request`（必须由用户手势触发，不能页面加载时自动弹） | 需单独说明范围与关闭方式 |
| `contextMenus`（可选） | 右键书签建标签 | 安装期 | 轻量 |

隐私三条硬约束：

1. 所有信号只在本地计算，**不出本机**
2. 工作台提供"清空学习数据"，一次删除全部 `kind=auto` 记录
3. 关闭 `tags.enabled` 后停止一切采集，已有数据保留但不再展示

## 8. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 面板塞满垃圾候选 | 用户放弃功能 | 常用区只留 3 槽 + 三级噪声过滤 + 三次删除拉黑 |
| 与浏览器书签栏认知重叠（"这不就是书签栏"） | 价值感知弱 | 差异化卖点：**全程键盘、零鼠标、`@` 一个字符** |
| 中文输入法触发跳动 | 体验割裂 | FR-10，组合期冻结候选 |
| 误跳成本高 | 信任受损 | FR-18 撤销 + 面板显示完整 URL 供核对 |
| 标签过多导致面板过长 | 首屏失焦 | 固定区 ≤ 8、常用区 = 3、其余靠输入过滤 |
| 打分衰减让标签"自己消失" | 困惑 | 固定项不参与衰减；自动项消失前先在"常用区"降权而非直接移除 |

## 9. 验收标准

1. 全新安装、不申请 `history`，正常使用 3 天后"常用区"候选 ≥ 3 个
2. 输入 `@` + 2 个字符，目标标签稳定出现在前 3 位
3. 100 条标签下，一次按键到面板重绘 < 30ms
4. 中文输入法连续输入 10 个字符，候选不出现闪烁或错位
5. 关闭 `tags.enabled` 后，`@` 完全退回普通搜索行为，无残留面板
6. 清空学习数据后，`kind=manual` 标签完整保留
